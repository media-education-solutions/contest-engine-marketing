# Database migrations

Versioned, auditable schema via [dbmate](https://github.com/amacneil/dbmate). No ORM,
no autogenerated diffs — plain ordered SQL files in `db/migrations/`, applied in
filename order, recorded in a `schema_migrations` table.

## Commands

```bash
npm run db:new -- <name>   # scaffold db/migrations/<timestamp>_<name>.sql
npm run db:migrate         # apply pending migrations
npm run db:status          # what's applied vs pending
npm run db:rollback        # undo the most recent migration
```

## Two connection strings, on purpose

- `NEON_DB_URL` — **pooled** (PgBouncer, transaction mode). What the app uses for every
  query, at all five call sites (`src/lib/*-delivery.ts`, the server actions).
- `NEON_DB_DIRECT_URL` — **unpooled/direct** (the Neon dashboard host without `-pooler`).
  What dbmate uses. Neon's own docs file schema migrations under direct connections:
  transaction pooling drops session-level features migration tools rely on —
  `SET`/`RESET`, session-level advisory locks, SQL-level `PREPARE`. `pg_dump` specifically
  needs `SET`.

Do not consolidate these into one variable. The app keeps using the pooled string; only
dbmate uses the direct one.

## `NEON_DB_DIRECT_URL` lives in `.env.local`, never in `.env`

This is the sharpest edge in the whole setup. `.env` in this repo is **committed on
purpose** (MED-35) — non-secret config that Vercel reads straight from the repo.
dbmate's `--env-file` flag defaults to `.env`, so the obvious move ("put the connection
string in `.env`") would commit a production database credential. `NEON_DB_DIRECT_URL`
goes in `.env.local` (gitignored) locally, and as a GitHub Actions repo secret in CI.
Never in `.env`.

## Why the npm scripts look repetitive

Each `db:*` script carries `$([ -f .env.local ] && echo '--env-file .env.local')` instead
of a plain `--env-file .env.local`. Don't "clean that up" — a plain flag pointing at a
missing file is a hard error for dbmate (exit 9), and `.env.local` never exists on a CI
runner. The conditional makes both branches work: locally it reads the connection string
from `.env.local`; in CI it falls through to `NEON_DB_DIRECT_URL` already in the process
environment (the GitHub secret), which dbmate also picks up — process env always wins
over the env file when both are present.

## Rollback is local-only

`db:rollback` drops whatever the most recent migration created. Every migration's
`-- migrate:down` section carries a warning comment for this reason — never run it
against production to "undo" something; write a new forward migration instead.

## Migration ordering: additive before destructive

CI applies pending migrations on merge to `main`, before the Vercel deploy finishes.
That's the right order for additive changes (new table, new nullable column) — the
schema is ready when the new code arrives. It is the **wrong** order for destructive
changes (dropping a column) — the still-running old deploy breaks. Destructive schema
changes need the standard expand/contract split: ship a migration that stops using the
column first, deploy, *then* drop it in a later migration.

## Schema dump is off

Every `db:*` script passes `--no-dump-schema`. dbmate's dump shells out to `pg_dump`,
which fails outright when the local client's major version trails Neon's server — a
near-certainty against a managed Neon project. The dump (`db/schema.sql`, a live
snapshot for diffing) is a genuinely useful artifact; turn it back on once whoever runs
this has a matching `postgresql-client` installed.

## Known limitation: preview deploys share the production database

Migrations only apply on merge to `main`. A Vercel preview deploy running unmerged code
points at the *same* Neon database as production, so a preview whose migration hasn't
landed yet can hit a schema missing its columns. Tolerable today because changes here
are additive-only on a low-traffic marketing site. The real fix is a Neon branch per
preview deploy — out of scope for this ticket, noted here so it isn't rediscovered as a
surprise bug.
